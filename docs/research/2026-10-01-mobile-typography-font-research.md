# Mobile app typography research

**Reviewed:** 2026-10-01. **Scope:** the seven families in the supplied post, commercial mobile app embedding, and Expo SDK 57. Sources below are the font creators, foundries, license owners, or Expo.

## Expo SDK 57 constraints

Expo’s SDK 57 `expo-font` package is `~57.0.4`. Expo recommends the config plugin for native Android and iOS builds because it embeds fonts at build time; `useFonts` is the runtime option. The plugin needs a development build and does not work in Expo Go. Expo’s plugin supports TTF and OTF on both native platforms. ([SDK 57 `expo-font` docs](https://docs.expo.dev/versions/v57.0.0/sdk/font/), [Expo font guide](https://docs.expo.dev/develop/user-interface/fonts/))

Expo’s current font guide says variable font support on Android and iOS starts in SDK 58; earlier SDKs should use static files. SDK 57 maps to React Native 0.86, while Expo says direct `fontVariationSettings` support starts with React Native 0.88 / SDK 58. ([Expo font guide](https://docs.expo.dev/develop/user-interface/fonts/), [SDK version mapping](https://docs.expo.dev/versions/v57.0.0/))

For SDK 57, use static `.ttf` or `.otf` files for each needed weight/style. In Expo’s config, Android can map file paths to a family, weight, and style; iOS reads the internal family name from the font file, which may differ from its filename. Verify the resolved family name before assigning `fontFamily`. ([Expo SDK 57 font configuration](https://docs.expo.dev/versions/v57.0.0/sdk/font/))

## Practical shortlist

**Design judgment:** Manrope V5, Geist Sans, Cal Sans v2, and Space Grotesk are viable candidates for a clean product UI. Manrope V5 has a separate creator license, while the Google Fonts Manrope files are the older OFL build. Cal Sans v2 UI/Text is the most explicitly tuned for interface components, but its cut must be static for SDK 57. Space Grotesk has more visible character from its Space Mono heritage. Aeonik and Helvetica Now need paid app licensing; Satoshi is commercially free, but its content-authoring clause needs an interpretation for a chat/task app. These are typographic-fit judgments, not claims that one font is inherently more accessible or professional. ([Manrope V5](https://www.sharanda.com/manrope), [Geist](https://github.com/vercel/geist-font), [Cal Sans](https://github.com/calcom/sans), [Space Grotesk](https://github.com/floriankarsten/space-grotesk), [Aeonik](https://cotypefoundry.com/licensing), [Helvetica Now](https://www.monotype.com/fonts/helvetica-now), [Satoshi](https://fontshare.com/licenses/sil-ofl))

For Track, **Manrope V5 Static is the first candidate I would prototype** for a restrained, readable product UI. Its creator explicitly permits commercial app embedding and recommends the static files for small text clarity. Keep the original file unchanged and include the required name and attribution. Compare it with **Cal Sans v2 UI/Text Static** if compact controls and aligned badges matter most, and **Geist Sans Static** if a more Swiss, neutral character is preferred. Test the same real screens before deciding; this is a design recommendation, not a claim that the font is objectively best. ([Manrope V5 terms and small-size guidance](https://www.sharanda.com/manrope), [Cal Sans cuts](https://github.com/calcom/sans), [Geist](https://github.com/vercel/geist-font))

## Track role map

Use one sans family across app-owned interface text and reserve a real monospace family for fixed identifiers such as task keys. Keep the existing mobile design guide's type scale as the starting point, then assign semantic tokens so each screen uses the same role consistently:

| Role | Starting style | Use it for |
|---|---|---|
| Display | 28/34, bold | A screen's main heading and prominent empty-state title. |
| Title | 20/26, bold | Section headings and the main task-detail title. |
| Subtitle | 17/22, semibold | Channel and project titles, list-item titles, and navigation titles where space allows. |
| Message | 16/22, regular | Chat and thread text, composer text, and longer user-written content. |
| Body | 15/21, regular | Descriptions, task details, explanatory copy, settings rows, and search results. |
| Control | 15/20, medium or semibold | Buttons, tabs, menu actions, and selected filters. |
| Label | 13/18, medium | Form labels, field names, task attributes, and compact section labels. |
| Caption | 12/16, regular or medium | Helper and error text, timestamps, author and channel metadata, counters, pills, and status badges. |
| Identifier | 11/15, monospace | Task keys and other fixed-format identifiers only. |

Apply those roles to every app-owned surface: sign-in and onboarding; company and project pickers; project home; channels, threads, inbox, and message composer; task board, list, detail, and task creation/edit forms; search and filters; settings and profile; navigation bars and tabs; menus, sheets, dialogs, date pickers, empty states, loading states, errors, toasts, and confirmation prompts. A pill or badge uses the same caption or label token as its semantic content; it does not get an unrelated decorative font. Keep timestamps and names in the sans family, and do not use monospace to make ordinary metadata look technical.

Keep platform-owned UI and accessibility behavior intact. Do not disable dynamic type or font scaling to preserve a mockup. Check long translations, large accessibility text, narrow devices, text wrapping, numeric alignment, contrast, and font-weight availability on both iOS and Android. Keep sentence case and avoid all-caps labels, which become harder to scan at small sizes.

## Implementation map for the mobile app

The app already has a shared `Fonts`/`Typography` theme and a `ThemedText` component, and Expo's `expo-font` package is installed. But the project instructions currently disagree on the default family, and some components set local font styles directly. Resolve the design-doc conflict first, then route all app-owned text through the shared semantic roles. Audit raw React Native `Text` and `TextInput`, navigation options, buttons, pills, tab labels, calendar/date controls, and third-party components because changing the shared default alone will not replace every local override.

For SDK 57, bundle official static weight files and map regular, medium, semibold, and bold deliberately. Do not fake a missing weight with the nearest available file. Expo's native font config plugin bundles those files into native builds; `expo-font` is already present, but a new development/native build is needed to verify the packaged fonts on device. Keep font files and their required license or attribution notices together, and do not alter Manrope V5 or fonts whose license forbids conversion. Complete the visual audit on both platforms before calling the migration done. ([Expo SDK 57 font configuration](https://docs.expo.dev/versions/v57.0.0/sdk/font/), [Manrope V5 terms](https://www.sharanda.com/manrope))

## Track mobile decision

Track Mobile uses Manrope V5 Static for app-owned text, with platform system fonts for native controls and glyph fallback. The original static files are bundled with their license notice, and the required attribution appears in the account's Fonts and licenses section. The web app retains its separate Inter and Geist direction. The decision and role rules are recorded in [`apps/mobile/STITCH-DESIGN-RULES.md`](../../apps/mobile/STITCH-DESIGN-RULES.md) and [`apps/mobile/mobile-ui-ux-guide.md`](../../apps/mobile/mobile-ui-ux-guide.md).

the combined Company/Tasks/Threads product shipped to production, reliable push
notifications were built end to end, fabricated store screenshots were replaced
with honest ones, and Track 1.1.0 went to both stores.

## Production ship and rollback (07-13)
Shipped seven commits, then hit two production failures in a row:

1. Review found a P1 — server auth always preferred production Convex aliases in
   local development. Fixed in `b2fe94a`, deployed, and **live Chrome immediately
   failed**: `/workspace` rendered "Something went wrong" with an invalid `op://`
   Convex deployment address baked into the client bundle. Rolled production back
   to healthy version `dfd65b8e` within a minute.
2. Root cause was an unsafe production client fallback to development/base URLs.
   Removed it, required an explicit production Convex client URL (`20c1184`), and
   verified the generated artifacts contain the real URL with no unresolved
   `op://` reference before redeploying.

**Records were only half-removed.** Production web was on the Records-free bundle,
but read-only Convex inspection found `records.js:*` and `exports.js:*` still
deployed with the `records`, `draftRecords`, `aiReviews`, and `exports` tables
intact — the July 11 source commit's Convex half had **never been deployed**. A
production dry run then failed because Better Auth's Kysely adapter imported
migration constants absent from the installed Kysely export surface; Better Auth
**1.6.15** was the smallest compatible release (1.6.23 bundled but failed
monorepo typecheck). Cleanup removed 1 Record, 2 Draft Records, 13 AI reviews,
5 exports, 20 legacy audit events, 75 legacy permission/settings fields, and three
obsolete assistant-response passages, then dropped the four empty tables. Note:
historical assistant messages still contain old "Draft Record" language because
the removal never rewrote conversation history.

Also removed invitation and audit subscriptions from the workspace rail for
privacy (`53e7b06`), defaulting the rail to collapsed.

## Channel membership — two hotfixes
**Header avatars (`ad1ac14`):** the workspace header was sourcing members from the
Project member list rather than the selected Channel's membership query. During
deployment, the generated config uploaded to an unintended `track-web` Worker and
the custom domain returned HTTP 500; the real production Worker is `track`.
Redeployed correctly, restored all routes to 200, and deleted the accidental
Worker.

**Legacy membership (`25bb8b1`):** the strict active-status filter shipped in the
previous fix **dropped historical members** — production had 76 Channel-membership
rows, of which 75 legacy rows omit `status` entirely. Added shared legacy/Company
active-membership semantics and wired the selected-Channel projection into
authorization visibility, member listing, header avatars, composer copy, and
mentions. Membership activity now resolves from the parent Project access profile
rather than row shape; the server stays authoritative and the client only rejects
wrong-Channel/stale rows and missing users. Codex review caught a P2 where
forwarding-note mentions used the *source* Channel projection.

## Mobile push notifications — spec to production
**Planning:** the existing spec described the work as greenfield, but an audit
found a **partial native push path already shipped** (Expo token registration,
delivery, foreground presentation, tap routing, membership-aware filtering).
Rewrote it to distinguish the existing prototype from the desired release state.

Hasan chose all eligible activity by default, contextual permission/privacy
posture, and Expo transport if it can meet the goal. Confirmed against official
docs that Expo supports the needed features but is **best-effort, at-least-once,
has no SLA, and cannot prove final OS display**; recorded its 100-message request
limit, 1,000-receipt limit, 600 notifications/second/project, ~15-minute receipt
check guidance, and 24-hour receipt retention. A late finding from Expo's FAQ:
payloads are not persisted but **may be visible to Expo staff during active
debugging**. That drove the privacy decision — Hasan chose security-minimizing
payloads with useful context: copy like "Bilal mentioned you in #launch-readiness"
carrying only sender, event kind, Channel/thread, task key, and Project, with
message bodies, task titles, comments, filenames, references, assistant output,
and imported memory all excluded.

**Implementation (`880d072`, `ef90747`):** account-owned push installations,
durable notification event/intent/attempt records, idempotent creation,
100-message Expo batches, access-token auth, bounded retry, receipt
reconciliation, invalid-token cleanup, environment isolation, contextual
permission education, exact message/thread/task routing, response deduplication,
foreground suppression, token refresh, safe sign-out detachment, and
account-switch claiming.

Two bounded Codex reviews found **thirteen defects** between them — legacy-token
cleanup on sign-out, server-environment preservation for older clients, Expo-token
refresh after APNs/FCM rotation, scheduled recovery for batched intents, bounded
badge reads, atomic partial preference updates, sign-out failure feedback, Android
13 permission ordering, malformed Expo-response recovery, receipt-job fan-out,
reactivation of invalid legacy tokens, old-message exact navigation, and foreground
badge suppression. All fixed with regression coverage.

**Verification** ran on disposable simulators. iOS: permission prompt and allowed
state proven; `simctl push` proved background and terminated banners plus tap
routing; **denied state not capturable** because `simctl privacy reset
notifications` failed with `Operation not permitted`. Android: the app sat on a
loading spinner until it turned out the missing piece was an `adb reverse
tcp:3000` for the auth/web bridge alongside Metro's 8083. The in-app notification
screen still reported `Default FirebaseApp is not initialized`, so real
provider-delivered Android banners remain unproven, and no synthetic tap-route
claim was made because Android rejected the shell content intent
(`getIntentSender()` permission denial).

Expo **Enhanced Security for Push Notifications** was enabled on `@q9labsai` after
provisioning an organization-scoped robot token (a personal token was insufficient
— the org page only exposes robot-user tokens).

## Track 1.1.0 to both stores
Version set to 1.1.0, iOS build 24, Android versionCode 13. Store listings were
rewritten — both live listings used vocabulary predating Channels, threads, and
tasks, and Apple's copy still referenced removed Records and exports.

Build failures along the way: iOS build 24 failed because EAS omitted optional
native packages; build 26 included them but `sharp` detected the worker's global
libvips and forced an unsupported source build; **build 27** succeeded on Node 24
ignoring global libvips.

Android was blocked entirely because Firebase project `track-494517` **had no
Android registration** for `ai.q9labs.track`. Authorized recovery created
`Q9 Track Android` and downloaded the canonical `google-services.json` (backed up
to 1Password, gitignored locally). Two more builds were canceled after archive
inspection: one because the ignored native Android project still declared
versionName 1.0.0, another because a stale generated `apps/mobile/android`
directory would **bypass Expo config plugins entirely** — fixed durably in
`c361410` by excluding it from EAS archives.

**Production push backend deployed** to `fleet-manatee-941`: eleven indexes across
`pushInstallations`, `pushDeliveryIntents`, `pushDeliveryAttempts`, and
`pushNotificationEvents`, all tables initialized at zero.

**App Privacy was wrong.** App Store Connect's product page said
`Data Not Collected`, conflicting with Track's published policy and actual
implementation. Submission was held until Hasan approved correcting it; nine data
types were then published (Name, Email, Emails or Text Messages, Photos or Videos,
Audio Data, Other User Content, User ID, Device ID, Other Diagnostic Data), all
linked to identity and none used for tracking.

Final: iOS 1.1.0 build 27 submitted as review submission `1e049c23`
(`WAITING_FOR_REVIEW`, manual release); Android versionCode 13 promoted to Play
production and `IN_REVIEW`, replacing versionCode 12.
